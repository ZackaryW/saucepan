# Release builds

The workflows in `.github/workflows/` adapt the previous Saucepan repository's
release and native-platform checks to this Rust-only package. There is no SDK
workflow: this repository ships the Rust manager and its Rust shim.

## Checks and publication

`core-platforms.yml` runs only on manual dispatch and calls from the release
workflow. Pull requests and ordinary branch pushes do not start hosted checks;
this keeps the full platform matrix an explicit CI expense. It runs formatting, Clippy,
all-target tests, packaging checks and the explicit native keyring round trip on
Windows, macOS and Linux. Linux tests run inside an isolated D-Bus/Secret Service
session because store initialization needs native key custody. A separate
Windows job checks all targets with the declared minimum Rust 1.89.

`release.yml` runs on a pushed `v*` tag or manual dispatch with an **existing** tag.
The tag must equal `v` followed by the version in that tag's `Cargo.toml`, such as
`v0.1.0` or `v0.2.0-rc.1`. Both paths check out the tag, resolve it to a commit,
and build and test that same commit. Manual dispatch does not package the latest
default-branch source under an unrelated version. Prerelease tags produce
GitHub prereleases, which Saucepan's `latest_stable` selector excludes.
The tagged commit must include this repository's release scripts and workflows.

Release packaging waits for the complete platform checks to pass, so failed
checks do not spend runner time on the six-target build matrix. Each build
uses `Cargo.lock`, builds both binaries, and sets `SAUCEPAN_BUILD_ID`
to the tag. Publication waits for every native check, target build, universal
package and archive validation. Only the publication job has `contents: write`.
Existing release assets are not overwritten; use a new version/tag for changed
bytes. Release notes are generated by GitHub.

## Assets

Each asset is named `saucepan-<tag>-<target>.zip`. The retained target matrix is:

| Platform | Targets |
| --- | --- |
| Windows | `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `i686-pc-windows-msvc` |
| macOS | `x86_64-apple-darwin`, `aarch64-apple-darwin`, `universal-apple-darwin` |
| Linux | `x86_64-unknown-linux-musl` |

Each ZIP has a flat root containing `saucepan`, `saucepan-shim` and `LICENSE`.
Windows executables include `.exe`. Both macOS universal binaries are combined
with `lipo`; the shim is not omitted. ZIP entries record executable permissions
explicitly. Archives are packaged before artifact upload, preserving the internal
mode metadata despite [artifact transfer's permission behavior](https://github.com/actions/upload-artifact#permission-loss).
`SHA256SUMS` records the hash of each of the seven ZIPs. These are checksums,
not publisher signatures or notarization.

For a Windows x64 GitHub release request, use an asset pattern such as
`saucepan-*-x86_64-pc-windows-msvc.zip` with `selection.platform` set to
`{"os":"windows","arch":"x86_64"}`, `format: "zip"`, and
`bin: ["saucepan.exe"]`. The shim is included for initial bootstrap or explicit
launcher maintenance. Routine managed self-update still changes the selected
application output rather than replacing the installed shim.

## Local verification and remaining evidence

The CI-only packaging helper uses Python 3.11+ standard-library ZIP/TOML support;
Python is not included in the release and is not a Saucepan runtime dependency.
Run its focused checks from the repository root:

```powershell
uv run --no-project python -B -m unittest discover -s scripts -p test_release.py
```

The tests check both binaries, archive executable modes, checksum contents, tag
validation, incomplete build sets, missing shims and overwrite refusal. Workflow
syntax can be checked with `actionlint`.

On 2026-10-10, both workflows passed `actionlint` (without optional ShellCheck or
Pyflakes), and all five packaging tests passed locally. A locked, offline Windows
release build produced both binaries; extracting the generated ZIP preserved
their SHA-256 hashes, and the extracted manager returned
`saucepan 0.1.0+v0.1.0` from `--version`. This was a local packaging check, not a
GitHub publication or an installed-shim acceptance run.

Adding workflows does not establish that hosted builds have passed. Native
Linux/macOS behavior, cross-target release builds and the Rust 1.89 job need
actual runner evidence. The full release-download/bootstrap/self-update/rollback
acceptance gap described in the [documentation map](README.md) remains separate:
building and publishing assets does not exercise Saucepan consuming those assets.

To publish, commit the intended version and lockfile, push that commit, then push
the matching tag to the destination GitHub repository. This workflow work does
not itself create a remote, push commits or tags, or publish a release.
